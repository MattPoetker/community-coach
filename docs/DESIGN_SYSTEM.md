# Design System

Four layers of tokens, one rule, and a lint that enforces it.

## Directions and themes are different things

This distinction is the one that matters, and getting it wrong is what produces six
products that look identical.

| | **Direction** | **Theme** |
|---|---|---|
| Owns | Layout, component anatomy, information model | Colour, type, spacing, radii |
| Answers | *What is on the screen and how is it arranged?* | *What does it look like?* |
| Ships as | Code — a stylesheet plus its layout components | Data — 14 values in `communities.branding` |
| Changed by | A developer, in a PR | An owner, in admin settings, live |
| Examples | Broadsheet, Console, Studio | Kiln, Hearth, Grove |

Kiln, Hearth and Grove are three themes of **one** direction — same sidebar, same card feed,
same right rail. Recolouring is all a theme can do, and that is correct: it is the layer an
owner is trusted with.

Dramatic variation lives one layer up. A direction can delete the card, replace the feed
with a split pane, or lead with media instead of text — because it is code, reviewed like
code. Crucially, a direction still consumes every Layer 2 token, so **every direction is
still fully brandable**. Open any direction preview and use the brand editor: the layout
holds, the palette and type move.

Ship a direction when the *shape* of the product should change for a segment. Ship a theme
when only its voice should.

## The one rule

**Components read Layer 2 and Layer 3 only.**

A component that references a Layer 0 or Layer 1 token, a raw hex value, a px radius or a
literal font stack is a whitelabel bug. It will look fine in development and then refuse to
respond to a community's branding in production. `pnpm lint:tokens` fails the build on any
of those, so the rule is checked rather than remembered.

## The layers

| Layer | What it is | Who writes it | Who reads it |
|---|---|---|---|
| **0 — Brand inputs** | ~14 values: accent, neutral, three fonts, radius/density/type scale | The community owner, in admin settings | `Branding::TokenCompiler` |
| **1 — Derived ramps** | 13 neutral steps, 9 accent steps, accent-contrast | Computed in CSS from Layer 0 | Layer 2 only |
| **2 — Semantic tokens** | `--surface-default`, `--text-secondary`, `--border-accent`, … | `tokens.css` | **Components** |
| **3 — Component tokens** | `--card-radius`, `--button-radius`, `--meta-font`, … | `tokens.css`, retuned by themes | **Components** |

Layer 1 exists in CSS rather than in Ruby on purpose: the admin brand editor can then move
a slider and repaint the whole interface with no round trip, because the browser is doing
the ramp derivation from three numbers.

## Files

```
web/styles/
├─ tokens.css          Layer 0 defaults, Layer 1 formulas, Layer 2/3 contract, dark mode
├─ themes.css          the six presets — Layer 0 + structural personality only
├─ components.css      the default direction's components, reading Layer 2/3 exclusively
├─ themes/*.json       the presets as data, for seeding and the admin picker
└─ directions/
   ├─ broadsheet.css   a publication: masthead, asymmetric grid, no cards
   ├─ console.css      a queue: split pane, one-line rows, keyboard-driven
   └─ studio.css       a broadcast: full-bleed hero, horizontal rails, media-first
```

A direction replaces `components.css` rather than extending it — different anatomy means a
different component layer. It keeps `tokens.css`, which is what preserves branding.

## Colour

Everything is OKLCH. Ramps are generated by holding hue and chroma and stepping lightness,
which is perceptually even in a way the equivalent HSL walk is not — an HSL ramp gets muddy
in the yellows and washes out in the blues, and no amount of hand-tuning fixes it for an
accent you have not seen yet. Since owners pick their own accent, the ramp maths has to
work for hues nobody on the project chose.

Neutrals carry a small chroma at a hue near the accent. A pure grey next to a saturated
brand colour reads as unconsidered; a grey with 0.005–0.04 chroma reads as part of the same
palette. `Ledger` deliberately breaks this, running a cool grey against a warm oxblood — the
one place that theme raises its voice.

## Dark mode

Three viewer states, not two. An explicit choice stamps `data-mode="dark"` or
`data-mode="light"` on `<html>`; the default system setting stamps nothing, and only
`prefers-color-scheme` separates the two.

So each dark ramp is declared twice: once under
`@media (prefers-color-scheme: dark) { :root:not([data-mode="light"]) }` and once under
`:root[data-mode="dark"]`. The duplication is deliberate — it is what makes an explicit
light choice beat a dark OS, and an explicit dark choice beat a light OS. Themes only
restate the handful of values that differ, because the Layer 2 mappings are shared.

Never style a component inside a media or `[data-mode]` block. Change the token; the
component follows.

## Adding a component

1. Write it in `components.css` using Layer 2 tokens.
2. If a theme would plausibly want to retune one dimension of it — a radius, a font, a
   transform — add a Layer 3 token in `tokens.css` with a Layer 2 default, and use that.
3. Add it to `preview/themes.html` so it is visible in all four themes at once.
4. Run `pnpm lint:tokens`.

Resist adding a Layer 3 token "just in case". Each one is a knob every future theme has to
have an opinion about.

## Adding a theme

Add a block to `themes.css` and a matching `themes/<key>.json`, then register the key in
`Branding::TokenCompiler::PRESETS`. A theme may set Layer 0 values and Layer 3 component
tokens, plus the structural properties (`--border-width`, shadows, leading, tracking,
weights). A theme that needs to override a Layer 2 mapping is a sign the contract is
missing a token — add the token instead.

Any new font must also be registered in `Branding::FontRegistry`, which is an allowlist for
two reasons: the family name is interpolated into a Google Fonts URL and into CSS, and
self-hosted installs need a known list to mirror locally for air-gapped deployments.

## The presets

Each is named for the customer archetype it serves, not for a colour — the point of having
several is that a self-hoster recognises their own practice in one of them.

**Kiln and its variations.** Kiln is the control. The two variations hold its warmth and
its relational tone, and move on the axes a client can actually articulate: how literary it
feels, and how much it asserts itself.

| Preset | Reads as | Ground | Accent | Display / body | Structure |
|---|---|---|---|---|---|
| **Kiln** | Friendly, approachable | Warm sand | Muted forest | Bricolage Grotesque / Karla | Radius 1.5×, soft hue-tinted shadows, roomy |
| **Hearth** | Literary, calm | Deeper oat — reads as paper stock | Dusty brick | Newsreader / Karla | Radius 1.0×, roomiest, biggest type contrast |
| **Grove** | Assured, contemporary | Warm grey | Deep teal | Epilogue / Figtree | Radius 0.9×, hairline-defined cards, neutral density |

Hearth keeps Kiln's Karla underneath, so the two read as relatives rather than strangers.
Its accent is held deliberately low in chroma: a saturated terracotta on warm cream is the
most over-used pairing in this category, and the dusty brick stays clear of it.

Grove is the one to reach for when the buyer is a business rather than a person — same
warmth, more composure.

**Other directions**, kept for reference and for installs that want them:

| Preset | Archetype | Ground | Accent | Display / body | Structure |
|---|---|---|---|---|---|
| **Meridian** | High-ticket mastermind | Deep petrol, dark by default | Warm coral | Instrument Serif / Hanken Grotesk | Elevation by luminance, not shadow |
| **Signal** | Performance coach | Cool near-white | Electric blue | Archivo / Schibsted Grotesk | 2px ink borders, square cards, round controls |
| **Ledger** | Professional practice | Cool grey | Oxblood | IBM Plex Sans / IBM Plex Mono | Near-square, no elevation, mono metadata, dense |

## Evaluating them

```bash
python3 -m http.server 8919
open http://127.0.0.1:8919/preview/index.html     # start here — all four directions
```

| Preview | What it shows |
|---|---|
| `index.html` | The four directions, and what each is for |
| `themes.html` | Kiln direction, product screens, all six themes switchable |
| `landing.html` | Kiln direction, public sales page |
| `broadsheet.html` | Broadsheet direction |
| `console.html` | Console direction |
| `studio.html` | Studio direction |

Same markup and same content in every theme, so the comparison is like for like. The two
pages share `preview/harness.{css,js}` — one switcher, rendered by the harness itself, so
it cannot drift between them. Your selection persists across both.

`themes.html` covers four product screens plus a component specimen. `landing.html` is the
community's public sales page, which follows the layout the category has settled on: a wide
editorial column carrying the offer (name and rating, media gallery with filmstrip, icon
meta row, owner-authored description, reviews) beside a narrow sticky card carrying the
decision (cover, short description, a Members / Online / Admins trio, and the join button).
Visitors arrive on that page from an ad or a creator's link already knowing how to read it,
which is reason enough not to reinvent it.

A note on the review cards: the "still a paying member after 14 months" line is the most
persuasive element on the page, because it answers the objection a visitor actually has. It
takes the semantic success colour rather than the accent — it is a fact about retention,
not a piece of branding.
